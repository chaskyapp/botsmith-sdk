# Proposal — developer keys instead of the platform secret

Status: **proposal. Nothing is built, on either side.**

Raised 2026-09-09. It changes who can administer bots, so it belongs in front of
the packaging decisions it would undo.

---

## The problem it solves

The admin surface today sits behind `X-Secret`, which is Chasky's **global API
secret**: one value, from `API_SECRET`, compared for equality by a middleware
that guards every non-public route on the API.

That has three consequences, and none of them is about bots:

1. **No third party can ever administer their own bots.** Handing them the
   platform secret would hand them the whole internal API. So the admin client
   had to be split into a separate package that only Chasky itself can use — see
   §6 of the contract.
2. **A leak is unattributable.** Every internal caller uses the same value, so
   there is no way to know which one lost it.
3. **Rotation is all-or-nothing.** Changing it requires redeploying every
   consumer at once. In an incident, that is the worst possible property: the
   fix is as disruptive as the breach.

## The proposal

A developer generates a key from a panel in Chasky, and the SDK takes **that**
key instead of the platform secret.

This is the shape Stripe settled on, and the parallel is close enough to borrow
from directly: a publishable key for the browser, a secret key for the server,
with the prefix making it obvious at a glance which is which. Telegram is no
guide here — it never exposed bot administration as an API at all, so it has no
equivalent to hand out.

```
sk_live_…   generated by a developer, scoped to what they own
```

### What it changes for the SDK

**The admin client stops being internal-only.** Right now it is a separate
package because its credential is a platform secret; with per-developer keys the
credential is the developer's own, and administering your own bots becomes a
normal third-party capability. D13 and the split in §6 would be revisited on
purpose rather than kept out of caution.

The runtime is untouched: bot tokens already work this way.

### What it needs from the server

None of this exists yet, and it is all server work:

- **Issue, list and revoke keys**, per developer, from a panel.
- **Store only a hash**, and reveal the key once at creation — the same
  discipline `SecretReveal` already follows for bot tokens.
- **Authenticate with the key**, rather than reusing `ValidateApiSecret`. A
  developer key must NOT open the rest of the API: that is the entire point.
- **Scope it.** A key administers the bots its owner owns, and nothing else.
  Without scoping this is the platform secret with extra steps.
- **A prefix that reads wrong in the wrong place** (`sk_`), so a key pasted into
  a browser bundle is visible in review.
- Optionally: expiry, last-used timestamps, and per-key audit — the things that
  make an incident diagnosable instead of total.

## Recorded as S6

Added to §13 of the contract alongside the other server requests. It is larger
than S2–S5 and unlike them it is not a papercut: it decides whether third
parties can manage their own bots at all.

## Until then

The admin packages stay as they are — separate, named for their audience, and
carrying the three guards added on 2026-09-09:

| Layer | Mechanism |
|---|---|
| Build | the `browser` condition in `exports` is `null`, so a bundler refuses to resolve it for a client build |
| Runtime | `assertServerOnly()` throws where `window` and `document` both exist |
| Type | `PlatformSecret` / `AsPlatformSecret(...)` — a bare string is rejected, so passing it is a line that reads wrong in the wrong file |

A caller on Next.js can add a fourth by importing `server-only` in whatever
wraps the client: that breaks the **build** if a client component ever reaches
it, which is stronger than anything this package can check about itself.
